{# The tool tree. One collapsible group per namespace, one visibility control per level. Every control posts to its own route and swaps this whole partial back in, so the three levels never render a stale mark. Two constraints shape the markup: - A tool name comes from the child, so it travels in the form body, never in the URL path. A child that names a tool `../../servers/x/delete` would otherwise produce a link the browser normalises into a different authenticated route. - Every control syncs on `#tools-tree` with `replace`, not `queue`. The response swaps this whole partial, so a queued request would be owned by a form the swap already detached, and htmx would drop it silently. `replace` cancels the in-flight request instead. Note this is cancellation, not ordering: the server may already have accepted the cancelled request, so two clicks inside one request window can still commit out of order. The next render corrects the page. - The namespace control sits just below its ``, not inside it. Clicking any child of a `` toggles the group, so a control placed there could not be operated without JavaScript. - The `mcpflow` group is the built-in admin server. It has no child, so its header shows `built-in` in place of a status and its namespace control reads `mcpflow_muted`, not `c.spec.muted`. The root does not cover it, so the root state never disables one of its controls. A pinned row carries a checked, disabled control: visibility never hides that tool, so the admin cannot lock themselves out of the MCP admin surface. #}
